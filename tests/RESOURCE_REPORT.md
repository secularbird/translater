# Android 资源实测：常驻与低内存模式

日期：2026-09-27。测试对象为当前已安装的 debug APK，不修改产品推理代码。

## 方法与口径

- Android 17 ARM64 模拟器，4 个逻辑核，`MemTotal=4061984 KiB`（约3.87 GiB），已存在完整离线模型缓存。
- 每个模式重新启动应用进程，依次测空闲、预热、VAD聆听、3次英文语音→中文翻译、停录15秒、再次录音、释放模型15秒，以及单独VAD运行8秒。
- 麦克风权限及原生采集正常运行；在生产VAD Worker输入处替换为9.152秒固定PCM（含尾静音），保持实际采集帧长与节奏。Silero、SenseVoice、M2M100、应用队列与UI全部真实运行，没有模拟识别或译文。
- 同时采样应用主进程及其WebView进程：内存约每0.5秒一次（常驻236个样本，低内存318个），CPU每1秒一次。峰值是**采样峰值**，不保证捕捉瞬时最大值。
- CPU **100%=占满一个逻辑核**，4核合计上限400%。CPU区间跨越阶段边界时不纳入分阶段统计；热态ASR约1秒，缺少完整落在阶段内的CPU区间，因此不报告其独立平均CPU。
- `PSS` 是分摊共享页后的物理驻留量；`SwapPss` 是换出页计量。Android17本机的摘要 `TOTAL PSS` 包含Swap，本脚本从分类行求和得到驻留PSS，避免重复计数。
- 下文“PSS+Swap”用于观察应用内存规模，**不是当前物理RAM占用，也不是压缩交换区实际占用字节**。RSS另列，多个进程RSS相加可能重复计算共享页。
- 宿主机同时运行其他应用，未隔离负载。本次不测实体手机、桌面版或6/8GB设备配置，也不做长时间稳定性或准确率评测。

## 内存结果

中位值用于相对稳定的阶段，峰值按同一个采样点的合计计算，不将不同时间的PSS峰值和Swap峰值相加。

| 指标 | 双模型常驻 | 低内存模式 |
|---|---:|---:|
| 未加载模型，PSS+Swap中位 | 291.6 MiB | 293.1 MiB |
| 整轮PSS+Swap峰值 | **3036.4 MiB（2.97 GiB）** | **2649.6 MiB（2.59 GiB）** |
| 整轮物理驻留PSS峰值 | 2172.5 MiB | 2189.7 MiB |
| 整轮RSS合计峰值 | 2341.9 MiB | 2364.0 MiB |
| 整轮SwapPss峰值 | 1081.9 MiB | 515.5 MiB |
| 完成翻译并停录，PSS+Swap中位 | **2818.5 MiB（2.75 GiB）** | **2058.6 MiB（2.01 GiB）** |
| 上一行中的驻留PSS中位 | 1771.4 MiB | 1848.7 MiB |
| 上一行中的SwapPss中位 | 1047.0 MiB | 210.3 MiB |
| 释放模型后，PSS+Swap中位 | 299.5 MiB | 308.4 MiB |

结论：低内存模式使本轮应用内存规模峰值降低约**13%**、停录保留量降低约**27%**。本轮两种模式的物理驻留峰值相近，差异主要体现在换出量；不能只看RSS判断收益。低内存模式在完成翻译后保留M2M100，仍占约2 GiB，并不会恢复为空界面占用。

第一轮未校准CPU阶段标签的常驻预跑也完成3次推理，PSS+Swap峰值3047.7MiB、停录中位2828.9MiB，与最终内存结果接近；预跑CPU分阶段结果不采用。

### VAD 增量

释放两大模型后单独启动生产VAD Worker：

- 常驻测试进程：VAD运行期间PSS+Swap中位326.8MiB，相邻无VAD基线299.5/276.0MiB，差值约**27–51MiB**。
- 低内存测试进程：对应349.8MiB与308.4/300.6MiB，差值约**41–49MiB**。

可按**几十MiB量级**理解这次VAD运行时增量。基线前后有垃圾回收、JIT和缓存变化，这不是模型张量内存的精确拆分。资源大头仍为识别和翻译模型。

## CPU结果

| 阶段 | 常驻模式（100%=1核） |
|---|---:|
| 停录常驻，平均 | 3.6% |
| 实际录音＋VAD，稳定阶段平均 | 23–25% |
| 释放大模型后，仅VAD阶段总平均 | 9.4% |
| 翻译阶段有效区间平均 / 峰值 | 197% / 207%（仅2个完整区间） |
| 加载翻译模型阶段有效区间峰值 | 295% |

低内存模式含重新加载的翻译阶段有效区间平均约194%、峰值332%。这些数字包含WebView、JS、垃圾回收和采集等进程开销；即使模型推理线程配置为1，也不代表整个应用最多只使用1核。采样和DevTools连接本身也有开销。

## 耗时与模型加载次数

| 指标 | 双模型常驻 | 低内存模式 |
|---|---:|---:|
| 第一次点击开始→进入录音 | 7.20秒 | 8.01秒 |
| 停录后再次点击开始→录音 | 0.93秒 | 3.93秒 |
| 第1次播放输入→译文完成 | 11.79秒 | 21.67秒 |
| 第2次播放输入→译文完成 | 9.97秒 | 24.85秒 |
| 第3次播放输入→译文完成 | 9.91秒 | 35.68秒 |
| 第2/3次ASR请求耗时 | 0.99 / 1.00秒 | 5.70 / 8.11秒 |
| 第2/3次翻译请求耗时 | 1.62 / 1.53秒 | 11.73 / 20.17秒 |
| 结束检查时模型加载次数 | ASR 1 / 翻译 1 | ASR 4 / 翻译 3 |

整条输入计时包含实时播放和端点等待，不是纯推理时间。低内存的请求计时包含重新初始化；ASR第4次加载发生在末尾第二次启动录音时。识别中仍有gold/code等误识别，原始输出完整保存在JSON，不以资源测试成功代表翻译准确。

此前启动54秒甚至81秒的观测，本次没有复现；两次常驻资源测试的首次启动为8.01/7.20秒、再次0.95/0.93秒。历史慢启动保留为波动记录，不作为固定耗时，也不能仅凭本轮断定此前慢启动的原因。

## 资源预算结论

- 当前常驻版，应用自身应按**约3GiB加余量**规划；加载瞬态和更长输入可能超过这次短句采样。
- 4GB模拟器可以完成流程，但常驻时约1GiB换出，不能将“跑通”当作“4GB设备都能流畅”。设备总内存建议8GB更宽裕；6/8GB是真机适配建议，不是本次验证结果。
- 低内存模式节省部分内存，却让这次连续声译明显变慢；实时体验优先时仍采用双模型常驻。
- VAD新增资源为几十MiB量级，优化内存应优先看SenseVoice/M2M100与WASM运行时。
- 本次结束已释放测试加载的模型、撤除PCM替换、恢复用户保存的设置，保留模型缓存。
